# UI-first 3v3 数据契约

第一阶段先建立与 MQTT、Protobuf 和 LIF 固件无关的比赛数据模型。目标是让
Mock、本地回放和后续真实协议共用同一份界面输入。

## 数据流边界

```text
Mock / 回放 / 新赛季协议适配器
                ↓
          MatchSnapshot
                ↓
          MatchSession
                ↓
      现有 QML 数据适配层
```

第一阶段只实现 `MatchSnapshot` 和 `MatchSession`。它不启动网络、图传、模拟
比赛时钟或任何实车控制。

## 快照结构

`MatchSnapshot` 包含：

- 比赛 ID、赛项和阶段
- 剩余时间和回合
- 红蓝双方队名、比分和机器人列表
- 有序比赛事件
- 整体更新时间

每台机器人包含：

- 唯一 ID、车位、阵营和角色
- 血量、弹量、热量和热量上限
- `energy`：超电百分比、缓冲能量、底盘能量、功率及各自上限
- `chassis`：底盘模式、驱动类型、使能状态和超功率断电时间
- `wheelLeg`：轮腿模式、车身姿态、轮速和可选关节角度
- 在线、存活和复活剩余时间
- 可选地图坐标、朝向和单项数据更新时间

功率统一使用瓦特（`W`），能量统一使用焦耳（`J`），超电使用百分比，长度使用
毫米（`mm`），角度使用度。未知状态统一使用 `-1`，地图位置另由
`hasPosition` 表示。`-1` 不能当作 0 显示，界面应转换为 `—` 或“等待数据”。

轮腿详细遥测由 `telemetryAvailable` 表示。关节以名称、当前角度和目标角度
组成，不预设具体数量和左右顺序；没有实车协议时允许为空。

## 校验规则

3v3 快照必须满足：

- 赛项为 `rmul3v3`
- 每队恰好三台机器人
- 机器人阵营与所在队伍一致
- 车位在队内唯一，机器人 ID 在全场唯一
- 已知血量不能超过最大血量
- 超电必须在 0 到 100% 之间
- 已知缓冲能量和底盘能量不能超过各自上限
- 轮腿关节名称必须唯一，关节角度必须是 -180 到 180 度
- 存在轮腿关节数据时必须标记详细遥测可用
- 已知地图位置必须位于 0 到 1 之间
- 已发生事件序号不能重复

有错误的新快照不会替换 `MatchSession` 中上一份有效状态，避免界面短暂显示
不完整比赛数据。警告会保留在快照中，但不阻止更新。
