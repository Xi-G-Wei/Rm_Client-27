# UI-first 3v3 数据契约

第一阶段先建立与 MQTT、Protobuf 和 LIF 固件无关的比赛数据模型。目标是让
Mock、本地回放和后续真实协议共用同一份界面输入。

## 数据流边界

```text
Mock / 回放 / 新赛季协议适配器
                ↓
          MatchSnapshot
                ↓
          MatchSession
                ↓
      现有 QML 数据适配层
```

第一阶段只实现 `MatchSnapshot` 和 `MatchSession`。它不启动网络、图传、模拟
比赛时钟或任何实车控制。

## 快照结构

`MatchSnapshot` 包含：

- 比赛 ID、赛项和阶段
- 剩余时间和回合
- 红蓝双方队名、比分和机器人列表
- 有序比赛事件
- 整体更新时间

每台机器人包含：

- 唯一 ID、车位、阵营和角色
- 血量、弹量、热量、热量上限和底盘功率
- 在线、存活和复活剩余时间
- 可选地图坐标、朝向和单项数据更新时间

未知状态统一使用 `-1`，地图位置另由 `hasPosition` 表示。`-1` 不能当作 0
显示，界面应转换为 `—` 或“等待数据”。

## 校验规则

3v3 快照必须满足：

- 赛项为 `rmul3v3`
- 每队恰好三台机器人
- 机器人阵营与所在队伍一致
- 车位在队内唯一，机器人 ID 在全场唯一
- 已知血量不能超过最大血量
- 已知地图位置必须位于 0 到 1 之间
- 已发生事件序号不能重复

有错误的新快照不会替换 `MatchSession` 中上一份有效状态，避免界面短暂显示
不完整比赛数据。警告会保留在快照中，但不阻止更新。

## 后续阶段

下一阶段实现 JSON 场景和比赛时钟，持续生成 `MatchSnapshot`。之后再通过
适配层连接当前 QML，并逐步加入受伤、离线、复活和结算场景。
